# 03. Validator — проверка и порог

Два контура, оба обязательны. Python-часть — детерминированные функции;
LLM-часть — модель отвечает по пунктам. Промежуточный вывод LLM не влияет
на итог: **PASS/FAIL считается по кодам из схемы (раздел 5)** —
LLM-ответ используется только когда Python не может решить пункт сам
(тон, стиль, «повышался ли уровень»).

## 1. Проверки Python (детерминированные)

| Код | Пункт | Что проверяется |
|-----|-------|-----------------|
| B1 | Блокировка уровня | `current_tier == target_tier` AND `offer_id` ∈ {LOY-UP-002, LOY-UP-003} → FAIL. Плюс: в тексте оффер уровня не может быть оформлен как «вы уже на уровне X» при X == current_tier. |
| F1 | Факт-чек: цифры | Все числа из текста (₽/числа/«N месяцев») сверяются с карточкой: `benefit_month_rub`, суммы и пороги из `conditions`. Число из текста, не совпадающее с полем карточки → FAIL. Выгоды нет в тексте (benefit_month_rub == 0) — ок; benefit > 0 и нет в тексте — см. V3 (покрытие). |
| F2 | Факт-чек: условия | Каждое условие из `conditions` отражено в тексте CARD. Добавлены условия, которых нет в карточке → FAIL. |
| R1 | Правила уровней | В тексте нет противоречий `loyalty_level.csv` (пороги трат/продуктов по уровням: silver ≥ 40 000 ₽ и 1 продукт; gold ≥ 100 000 ₽ и 3 продукта). |
| D1 | Дисклеймер | **На финальном тексте после постобработки**: дословно (посимвольно) содержится строка дисклеймера из `rules.csv` по `offer_id`. Python проверяет на финальном тексте, потому что сам дисклеймер вставляет Python (spec/04). |
| P1 | «Дополнительно запрещено» | Для offer_id: запретные слова/ситуации из `rules.csv` — `premium/элитный` (LOY-UP-002), сравнение с банками (LOY-UP-003), «кэшбэк на все покупки» (CASH-CAT-011), «доход/доходность/заработаете» (SAV-RATE-004), умалчивание о платном продлении (SUB-BUNDLE-007), «бесплатно» без условия (FEE-WAIVE-009). Плюс универсальный стоп-список от инъекций (кредит, предодобрен, ссылка, «игнорируй инструкции»). |
| T1 | Только русский язык | В PUSH и CARD любая буква должна быть кириллической. Единственное исключение — латинские слова самого канонического названия оффера (`Silver`/`Gold`, spec/05): это факт, а не смешение языка. Любая другая нерусская буква (латиница, посторонний алфавит) → FAIL с указанием, в каком блоке (PUSH/CARD) и какой символ найден. |
| T2 | Нет аномальных повторов символов | Один и тот же символ (кроме цифр — легитимные числа вида «300 000» не считаются) не должен повторяться подряд 3+ раза («ааа», «!!!») — это признак сбоя генерации модели, а не осмысленный текст. FAIL с указанием блока, символа и числа повторов. |

## 2. Проверки LLM (отвечает по пунктам)

| Код | Пункт | Вопрос к LLM |
|-----|-------|--------------|
| L1 | Уважительное общение | «Текст уважительный, без давления, страха, обещаний сверх данных? Да/нет + причина» (при vulnerable_client — строже: без «только сегодня», «поторопись», «вы уже…»). |
| L2 | Деловой стиль | «Текст сохраняет деловой стиль банка? Да/нет + причина» (без сленга, «крика», более одного «!»). |
| L3 | Повышался ли уровень (блокирующий) | «Предлагает/заявляет ли текст повышение уровня? Какой?». Нарушение, если **(a)** повышение предлагается при `current_tier == target_tier` в данных; или **(b)** заявлено, что клиент «уже» имеет целевой уровень, хотя в данных `current_tier != target_tier`. Легитимное предложение перехода (target старше current) — pass. Это **блокирующее событие** для дальнейшей функции (повторяет B1 по тексту, а не по полям). |
| I1 | Следы инъекции / чужие данные | «Текст содержит факты, обещания, ссылки или инструкции, которых нет в данных блока `<user_input>` и в каноническом описании Да/нет + причина». Ответ «да» = нарушение. |
| V3 | Покрытие информации | «Какой процент фактов карточки (название, выгода, условия) использован в PUSH+CARD? Проценты: PUSH отдельно, CARD/все вместе». Python извлекает числа из ответа; ≥ 75% → pass. |

## 3. Классификация пунктов и порог

**Обязательные (любой FAIL → отброс):**
1. B1 — блокировка повышения уровня;
2. F1 + F2 — соответствие предложения карточке (факт-чек);
3. R1 — верное указание правил уровней;
4. D1 — дисклеймер посимвольно;
5. P1 — отсутствие «Дополнительно запрещено».
6. L3 — повышение уровня не противоречит карточке (блокирующее событие,
   по тексту; дубль B1 на уровне LLM).
7. I1 — в тексте нет следов инъекций / чужих данных из `<user_input>`
   (второй контур после Python-скана P1 — «на всякий случай»).
8. T1 — текст только на русском (кроме латинских слов канонического
   названия оффера).
9. T2 — нет аномальных повторов символов подряд (сбой генерации).
   (плюс: формат-контроль spec/02 — обязательное условие входа в валидацию)

**Важные (нужны ≥ 2 из 3):**
1. L1 — уважительное общение;
2. L2 — деловой стиль;
3. V3 — ≥ 75% использование информации карточки.

**Желательные (не блокируют, только в лог):**
1. Креативность предложения (оценивает LLM, V4);
2. PUSH не повторяет дословно информацию CARD (V5);
3. 100% использование информации (V3 == 100%).

**Порог: PASS = (B1 ∧ F1 ∧ F2 ∧ R1 ∧ D1 ∧ P1 ∧ I1 ∧ L3 ∧ T1 ∧ T2) ∧ (≥ 2 из {L1, L2, V3}).**

## 4. Схема ответа validator (LLM)
Только один JSON-объект, без markdown:

```json
{
  "L1": { "pass": true,   "reason": "…" },
  "L2": { "pass": true,   "reason": "…" },
  "L3": { "pass": true,   "reason": "…" },
  "I1": { "pass": true,   "reason": "…" },
  "V3": { "pass": true,   "pct_push": 50, "pct_all": 80, "reason": "…" },
  "V4": { "pass": true,   "reason": "…" },
  "V5": { "pass": false,  "reason": "…" }
}
```
- Ключи только те, что в таблице (L1–L3, I1, V3–V5); лишние ключи игнорируются.
- `pct_push` — доля фактов, попавших в PUSH; `pct_all` — доля фактов в
  PUSH+CARD суммарно (критерий 75% — по `pct_all`).
- `pass` у V3 обязателен со стороны LLM, но **итоговый вердикт V3
  пересчитывает Python** из `pct_all` (≥ 75 → true).
- Нераспознанный/битый JSON от LLM → retry (spec/00); после 3 попыток →
  отброс.
- Python-коды (B1, F1, F2, R1, D1, P1, T1, T2, FORMAT) не входят в JSON
  LLM — их считает код. Для review (spec/02) итоговые нарушения собираются
  в одном списке: `[{"code": "F1", "blocking": true, "reason": "…"}…]`.
